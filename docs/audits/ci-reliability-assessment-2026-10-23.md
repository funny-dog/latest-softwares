## 需要解决的问题

### 1. P1：营销页与 64 KiB 验证窗口不匹配

位置：`packages/intl.yaml:4675`；`scripts/link_verifier.py:162`、产品身份检查。

Docker Desktop 的三个平台都使用 `https://www.docker.com/products/docker-desktop/`。本地用现有验证器复现同样的 unverified。额外做一次最大 512 KiB 的有界 HTTP 取样，响应约 263 KiB；首次 `Docker Desktop` 出现在字节偏移 81,368，title 出现在 83,617。现有 65,536 字节采样只读到前面的脚本，因此无法确认身份。

这是输入来源和读取策略的确定性不匹配，重试或提高 job timeout 无效。不能把 HTTP 200 当验证成功，也不应把宽泛的厂商名塞进 identity_terms。

解决方法：

- 优先把三个平台入口改成官方安装文档或官方文档明确指向的资产；每个平台单独核对。Windows 官方安装文档本地取样在前几百字节即包含产品身份和下载文字。用现有验证器分别真实检查 Windows、macOS、Linux 安装文档，三个候选均返回 verified；这只证明官方页面入口可验证，未下载或验签其安装包。
- 保持 mac-universal 为覆盖两个芯片选择的官方页面，或一起修改配置、覆盖基准和调用方后再拆成 mac-x64/mac-arm64；不要把单架构 DMG 误标为 universal。
- 通用验证器将二进制探测与 HTML 证据读取的预算分开。HTML 可分块读取至有界总量、优先解析标题/正文/链接，达到上限仍无证据就保留 unverified；二进制仍使用小样本，保留关闭流和重定向域名检查。
- 若修改算法，递增验证策略版本，避免旧缓存掩盖行为变化。仅修改 Docker 配置时，现有配置指纹即可触发重验。

验收：脚本前缀超过 64 KiB 的有效产品页能够识别；无产品身份的页面仍不能通过；HTML 总读取量有上限；三个平台分别验证，官网链接来源有证据。

官方依据：[Windows 安装](https://docs.docker.com/desktop/setup/install/windows-install/)、[macOS 安装](https://docs.docker.com/desktop/setup/install/mac-install/)、[Linux 安装](https://docs.docker.com/desktop/setup/install/linux/)。Windows/macOS 文档明确列出对应下载入口，macOS 分 Apple silicon 和 Intel。

### 2. P1：HTTP 暂时故障被当作确定失效，已有回退路径用不上

位置：`scripts/link_verifier.py:153-160`；`scripts/validate_links.py:214-264`。

网络层已经对 429/500/502/503/504 做有限重试，但重试后仍收到 502 时，校验器返回默认 failed。现有 transient 回退只接受维护页，或特定 network check failed 原因。Inkscape 因此丢失本轮可用状态，即使旧验证尚未到期，也阻塞发布。

解决方法：

- 将重试耗尽后的 500/502/503/504 分类为 transient；404/410、错误安装包、平台不符继续 failed；403/429 继续明确标记受限。
- 仅当 URL、平台、验证策略/配置指纹匹配，且原验证与签名有效期仍有效时，沿用原成功证据，并单独记录本轮失败尝试；不能延长 valid_until。
- 对阻塞必收录项设置较短的下次检查计划。当前 workflow 六小时才启动，代码中“30 分钟后重试”只表示下轮可检查，不保证半小时内实际执行。

验收：502 + 有效同指纹证据可携带原结果；原结果过期、换 URL/规则、无历史时仍不能通过；404 仍阻塞；重试次数和时长有界。

### 3. P1：最近成功证据没有完整保存，历史恢复可能给新 URL 错发验证

位置：`scripts/validate_links.py:84-118`、`:233-245`、`:276-292`。

状态只有当前 verification、last_success_at 和简化 history。一次失败会覆盖当前成功证据；history 没有保留原始有效期与配置指纹。恢复函数在找不到同 URL 成功记录时，直接回退到 last_success_at，再按七天重建 verified。

已用独立断言复现：历史只验证过 old URL，把当前资产换成 new URL，配合网络超时结果，恢复函数仍为 new URL 返回 verified。调用路径也没有在进入该恢复函数前强制要求旧指纹等于当前指纹。它不是本轮 Docker 失败的原因，但属于修复过程中引入的质量风险。

解决方法：

- 在现有 link-state 结构内保存完整的 last_success_verification 及其 fingerprint；失败只更新本轮 attempt 和退避，不销毁原证据。
- 恢复必须匹配 URL、平台、指纹和原始有效期；禁止仅凭一个软件/平台的 last_success_at 为未知地址生成成功证据。
- 快照回退也要核对验证规则身份，避免配置已变更仍沿用旧规则的结果。
- 原地址与官网 fallback 不应互相覆盖最近成功证据；按各自指纹保存或明确隔离成功记录。
- 对旧格式没有完整证据的记录保守重验；不要通过推算时间补造证明。

验收：跨 URL、跨配置、跨策略不得复用；失败运行后仍保留可审计的成功证据；缓存未命中不影响有完整匹配证据的恢复；不会延长签名或验证有效期。

### 4. P2：软件源配置已漂移，CI 通过也不代表版本和下载质量恢复

最新候选中 33 个 stale 软件，32 个原因涉及资源不匹配、匹配多个或 release 无所需二进制，另 1 个为 Ubuntu 请求超时。例子：

- PowerShell、Rufus、Transmission、Obsidian、LocalSend 等匹配多个资产，规则需要进一步区分版本/架构/安装与便携等变体。
- ShareX、Telegram、Another Redis Desktop Manager 等已有资产名称与配置模式不匹配，需要根据真实上游资源修正。
- Vaultwarden、Appsmith、NocoDB、n8n 等当前 release 不提供配置期望的桌面二进制，不能靠不断重跑恢复；需要选对官方分发形式。

此处只依据 CI 当次真实资产列表判断，未逐个确认最新上游分发情况，不能直接批量推导新 URL。

解决方法：逐项维护 packages YAML，优先复用 github_release/package_manifest；对无二进制的软件使用准确标注的官方安装页、容器或其他现有支持的分发入口。保持版本语义，不把同步日期冒充软件版本。保留目录覆盖，不通过删除重要软件或放宽多资产匹配来消除告警。

对于 67 个不可用入口，按“真实死链、重定向域名需核实、身份词/页面证据不足、访问受限、网络暂时故障”分组处理。优先重要软件与已确认 404；普通条目的问题进入有证据的维护清单，避免成功 CI 掩盖积压。

验收：每个新 pattern 对真实资产列表唯一匹配并满足平台要求；无匹配/多匹配仍失败；变更条目经过真实轻量链接验证；全量发布继续由同一快照门禁确认。

### 5. P2：代码检查、数据健康、发布新鲜度缺少清楚的职责边界

位置：`.github/workflows/sync.yml:85-109`、发布依赖链；`scripts/link_health_summary.py`。

- 完整共享 lint/test 只在 pull_request 事件运行。直接 push main 的修复会进入真实抓取与发布，但不执行这套代码回归检查；近期多轮修复正是 push 触发。
- 全局门禁是有意保护覆盖的设计，但任一必收录项卡住会冻结全部软件更新。旧线上快照不会立刻消失，不过前端 `web/app.js:233-237` 和下载 API 会按验证过期禁用入口；长期停止发布会扩大用户影响。
- 当前检查摘要混合本轮统计和缓存结果，容易误读“只有几条失败”或“很多失败导致发布失败”。部署 skipped 又容易被误当成部署平台异常。

解决方法：

- 让代码/配置 push 也执行现有共享检查，在发布前等待检查成功；定时同步可复用已通过检查的源码，不必每六小时重复整套离线测试。
- 保持候选 → 验证快照 → 两版产物链路。先做好上述暂时故障携带和稳定来源，不立即引入复杂的逐软件事务发布系统。
- 摘要明确列出 blocker ID/平台/原因、本轮尝试与缓存可用性、stale 软件、最近成功发布时间和临近过期的重要入口。
- 增加发布新鲜度检查：超过约定同步窗口仍无成功发布，或关键入口即将过期，给出可行动的失败原因；不要只看 workflow 结束是否绿色。
- 若将来仍需让其他软件继续更新，再设计按软件保留“完整、同版本、仍有效的上次包”，最终重新计算整个快照并运行原门禁；真实死链和缺少有效证据不得被该机制重新启用。

验收：push 中的逻辑回归能在联网发布前被挡住；定时上游故障与代码测试失败分开显示；两个部署仍绑定同一成功 run-id；失败发布不能覆盖线上成功快照；过期入口继续禁用。

另一个已复现的操作问题：`scripts/merge_results.py:62-69` 把所有未进入本轮分片的旧软件标为 stale。因此使用 workflow_dispatch 的 only/skip 做局部修复，会给正常但未调度的软件追加失败标记。应把本轮调度集合传入合并：未调度条目保留原状态，已调度但缺结果才标失败。验收用两个原本健康的软件、仅同步其中一个，另一个应保持健康。这不是上述定时失败的触发点，但会影响人工恢复流程。

独立 Gemini 只读审查已完成，结论已逐项与实际链路核对：采用上述局部同步问题；失败缓存属于有时限退避，不能称为永久死循环；link-state 裁剪在当前先全量合并再验证的链路里不能据此断言丢数据；本次日志未显示 Range 416 或并发提交冲突，不把它们列为已发生根因，也不建议为此直接放开分片完整性或盲目 rebase。
