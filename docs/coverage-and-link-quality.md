# 软件覆盖与下载质量

项目的优先目标是扩大收录、守住重要软件覆盖，以及保证下载/跳转正确。软件条目数不能替代有效覆盖率。

## 发布链路

`packages/ → sync 分片 → merge 候选 → validate_links --gate → README / 两版前端 → 发布产物`

- 配置是目录事实来源。合并阶段剔除已从配置删除的旧条目；新软件抓取失败时保留带原因的记录，必要时使用待验证的官方主页，不伪造发布版本。
- 链接修复必须重新验证，整个版本与资产一起更新；不会只换 URL 留下旧文件名、版本和大小。
- 每份快照有 `release_id`，API health 返回这个 ID。国内/国际部署按相同 Actions run-id 取验证数据、前端及对应源码，手动部署也只能选择成功的发布。
- 发布失败不会覆盖已部署版本；已有快照的验证有效期到期后，下载 API 会拒绝该入口，需要修复同步任务。部署产物保留 30 天，过期后须先运行一次成功同步。

## 必收录清单

`config/coverage.json` 是独立维护的必收录基准，声明软件 ID、分类、版本和应有的平台入口。初始包含 95 项，覆盖系统、浏览器、办公、通信、下载、开发、媒体、设计、安全及常用工具；这不是“全部重要软件已经穷尽”的证明，后续收录和需求反馈须持续补充基准。

```bash
uv run python -m scripts.catalog                 # 离线生成覆盖报告
uv run python -m scripts.catalog --gate          # 缺少必收录软件/有效平台入口则失败
```

`data/coverage-report.json` 区分：配置缺失、生成数据缺失、版本缺失、平台缺失、未经验证/不可用、目录外遗留数据。每个必收录平台必须有仍在有效期内的已验证入口；入口可以是准确标注的官网页面。

## 下载验证

```bash
uv run python -m scripts.sync --due
uv run python -m scripts.validate_links --gate
uv run python -m scripts.render
uv run python -m scripts.build_web --edition cn
uv run python -m scripts.build_web --edition intl
```

手动发布可显式提供 `--allow-unverified-required ID[,ID...] --exception-reason "人工批准原因"`。这只允许已存在、平台齐全但验证未通过的必收录条目作为发布例外；不会放行目录缺失、数据缺失、平台缺失或版本/edition 问题，也不会把资产改成已验证。前端与下载 API 仍禁用该入口。报告保存实际覆盖数量、`strict_gate_errors`、批准人、时间与原因，快照 `quality.publication_exceptions` 保存本轮例外。标志不从旧快照继承，定时运行仍是严格门禁。

Actions 的 `workflow_dispatch` 对应输入为 `allow_unverified_required` / `exception_reason`，默认均为空。2026-10-21 用户明确批准仅本次允许 `adobe-photoshop` 保留为待核验、禁用下载，其余软件仍必须通过原门禁。

### 长期例外（声明式，随配置走）

单次命令行豁免需要每次手动干预，不适合"上游长期反爬"这种稳定失败。这类情况改用必收录条目上的 `exemptions` 字段声明：

```json
{
  "id": "adobe-photoshop",
  "platforms": ["win-x64", "mac-universal"],
  "exemptions": {
    "reason": "Adobe 官网对自动访问返回 HTTP 403（反爬），无法自动核验",
    "review_by": "2027-04-01"
  }
}
```

生效规则（实现见 `scripts/catalog.py::_exemption_issue`）：

- **只放行 `restricted`**（上游拒绝访问/限流）。`failed`（404/410 等真实失效）**不在豁免范围**，仍会阻塞发布——避免把死链放行。
- **不允许豁免缺数据**：`package is None`（同步失败）一律阻塞，那不是反爬问题。
- **`review_by` 到期后自动失效**，需要重新评估上游是否仍拒绝访问。日期格式 `YYYY-MM-DD`。
- 被豁免的条目仍会以"待核验"状态出现在 README 和网站上，下载入口置灰，不会冒充可用。
- 豁免记录写入报告的 `required_exemptions`，便于审计。

当前生效：`adobe-photoshop`（`review_by: 2027-04-01`）。

仅在 `--gate` 成功后发布；本地调试可用 `--force` 忽略检查计划，`--budget N` 限制本轮验证操作数。默认预算 2000；预算不足的未知入口不能获得验证成功状态。

- 二进制响应最多读取 64 KiB；官方 HTML 页面最多读取 512 KiB，避免前置脚本挤掉产品证据。限制并发，不下载完整安装包，服务器忽略 Range 也会关闭流。
- 直链检查 HTTP、重定向、文件类型、部分格式文件头和文件名中的架构/平台冲突。不会把 HTTP 200 错误页当安装包。
- 下载页检查 HTML、软件身份和下载/购买/登录入口，忽略 script/style 内的字串，避免把程序中的产品字串或异常提示当作页面证据。需要 JS 才能确认、被封禁或无法确认的页面保留为待核验，不能假装成功。
- 初始目标来自人工配置或经 review 的 manifest；跨域跳转只有在精确域名清单中才放行。需要额外官方 CDN 时在软件 `verification.allowed_hosts` 填精确域名。不得用通配符放开任意下载域名。
- 软件名称在官网中不同，可用 `verification.identity_terms` 指定明确的软件身份词。避免填写过宽的厂商名、download 等通用词。
- 识别常见 AWS/Azure/Expires/P1 签名有效期，Windows ISO 另有保守有效期。未知签名格式无法保证识别，须补充对应解析器。
- 已确认不可用的直链，仅在官方页面也通过验证后降级；所有元数据保留具体来源。限制访问、网络失败、内容错误和待核验分别记录。
- 短暂网络失败、有限重试后仍返回的 HTTP 500/502/503/504 记为临时故障。仅在 URL、平台、配置/验证策略指纹一致且原验证仍有效时保留上次完整证据，记录失败尝试并安排重试；不能延长原有效期。
- **上游整站维护页记为 `transient`**，与 `restricted`（反爬/限流）、`failed`（404/410 等真实失效）三态区分：既不是死链也不是反爬，硬判失败会让整条发布流水线卡到上游恢复为止。识别措辞见 `scripts/link_verifier.py::_MAINTENANCE_PHRASES`（中英文维护通告）。仅当原验证仍有效时沿用上次结果，把重试提前到 30 分钟（`MAINTENANCE_RETRY_MINUTES`），到期后照常阻塞。旧验证已过期时 `transient` 不被复用，仍按失效处理。
- 前端/README 不提供已确认失效或过期资产的下载入口；API 返回 503 与 Retry-After。点击统计写入失败不会阻断有效下载跳转。

这些属于有界的来源和入口验证，不代表已完整下载计算 SHA256、验签、运行安装器，亦不构成软件安全认证。上游提供的 SHA256 是证据，未经完整下载不能宣称已校验文件哈希。

## 增量与历史

`--due` 按软件记录中的 `_sync` 调度：重要软件 6 小时、普通 24 小时、长尾 72 小时；下载页配置 72 小时。配置变化会立即失效缓存。失败按次数退避，最长 24 小时。

`data/link-state.json` 保存按软件/平台的最近检查、失败次数、下次检查及最多 10 次历史，并按指纹保留最多 10 份仍有效的完整成功证据，隔离原地址和官网 fallback。新快照验证结果也携带指纹，缓存丢失时可匹配恢复。仅有旧成功时间或简化历史不能重建 verified；已确认失效的指纹会被撤销，必须实际重验成功才能恢复。URL 或配置验证规则变化立即重检；修改验证算法时递增 `VERIFICATION_POLICY_VERSION`。失败运行的检查历史同样通过 Actions cache 保存，成功发布再写回仓库。入口验证默认有效 7 天，签名有效期更短时取更早时间。验证有效期和下次检查时间是不同概念。

发布门禁每轮重新检查不可用的必收录入口，避免上游恢复后仍被失败缓存退避阻塞；非必收录软件继续按退避计划增量检查。人工 `only/skip` 同步在合并时保留未调度软件的原状态，只把已调度但缺少结果的软件标记为 stale。

Actions 每 6 小时执行一次，实际及时性受任务排队、上游限制及失败影响；代码中的 6 小时是调度目标，不是 SLA。同步错误日志每轮清空，不把历史失败混进本轮失败率。

PR、push 和人工运行执行共享代码检查，publish 必须等待代码检查和链接门禁成功。定时运行复用已经检查的源码，不重复整套离线检查。链接摘要将必收录阻塞项排在前面，同时列出缓存中的不可用状态和 stale 元数据。统计定时工作流另运行 `python scripts/check_publication_health.py --max-age-hours 24`；仓库验证快照超过 24 小时未更新时该工作流报错，即使统计抓取仍正常也能暴露发布停滞。该检查反映仓库快照年龄，不证明云端部署成功。

`render --check` 按快照验证时间检查产物可复现性，避免 Windows ISO 在提交后过期造成无代码变化的 README 漂移误报；普通 render、前端和下载 API 仍按当前时间禁用过期入口。README 是静态发布记录，不能替代运行时有效性检查。

## 维护与验收

- 新增软件仍修改 packages YAML；重要软件同步加入 coverage 基准。
- 阿里云盘通过 `aliyundrive_official` 从官方页面的固定客户端 URL 字段取得版本和三平台资产，不执行脚本；缺字段、来源域名/文件名不符或客户端版本冲突时失败，随后仍走统一链接门禁。
- GitHub asset pattern 支持 `{version}`，替换为本次 Release 提取的版本号后再做 fnmatch；可精确区分同一 Release 的正式、便携、调试和架构变体，避免用固定版本位数猜文件名。无匹配或多匹配的规则仍不能冒充成功。
- 多源发现候选由 PR 人工 review，不自动合并。核对软件身份、平台、官方来源与许可限制，不能只看名称。
- 离线回归测试涵盖错误内容、错误架构、重定向域名、过期签名、修复复检、缓存、预算、覆盖缺口、上游维护页降级及两版快照绑定。
- CI 在 Windows 上抓取含 Fido 的分片，在 Ubuntu 上验证、构建和部署。真实 Windows/Fido、上游全量可达性及云端部署须由对应环境的工作流确认。

多源发现及稳定 ID 的持续版本刷新约定见 [多源发现说明](multi-source-discovery.md)。
